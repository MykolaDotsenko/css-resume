Working style

A few habits I rely on

Start from the data

When something breaks in production, I prefer to reproduce it against the actual data and trace the flow before changing code.

Be conservative with risky automation

If the system cannot distinguish two cases safely, I would rather keep an explicit review or unknown state than invent confidence.

Assume jobs will be retried

Syncs and important writes should be safe to run again. External input gets validated, and partial failures should not leave hidden corruption behind.

Keep the stack boring when possible

If a Django page or plain HTML/CSS is enough, I do not add another framework just to make the architecture look bigger.

The kind of problems I enjoy

Work where the input is messy but the person using the product still needs a clear answer: what changed, which data can be trusted, and what to do next.

Connect

I’m most interested in backend, data, and operational software.

Especially when the hard part is keeping data trustworthy across systems and turning it into a workflow people can rely on.
